# Tech Debt Tracker

## 一句话定位
追踪主仓当前技术债项，按影响和修复成本排序，形成可执行的治理清单。

## 核心内容
| ID | 债务项 | 影响范围 | 优先级 | 状态 | 计划修复窗口 |
|---|---|---|---|---|---|
| TD-001 | 主仓缺少统一 CI 门禁 | 全仓 | P0 | 进行中 | 2026-Q2 |
| TD-002 | 架构规则仅隐式存在于目录结构 | 核心与服务层 | P0 | 进行中 | 2026-Q2 |
| TD-003 | 文档入口分散、缺失 index 导航 | docs/ | P1 | 进行中 | 2026-Q2 |
| TD-004 | 子依赖与主仓边界未系统声明 | experiments/ | P1 | 进行中 | 2026-Q2 |
| TD-005 | 运行依赖和缓存前置条件散落 | 运维流程 | P1 | 进行中 | 2026-Q2 |
| TD-006 | 测试策略未形成统一主仓文档 | 质量体系 | P2 | 待处理 | 2026-Q3 |

## 修复计划
1. 先完成文档治理骨架与守卫脚本，形成统一执行路径。
2. 将守卫脚本集成到 CI，并让失败信息包含修复建议。
3. 在质量文档中明确可执行阈值，避免“通过标准”含糊。
4. 按模块收敛临时脚本和重复说明，减少知识分叉。

## Agent 行为指引
- 你应该在发现新债务时补充一条记录并给出优先级。
- 你应该把债务项链接到具体文件或规则。
- 你不应该只描述问题而不给修复方向。
- 你不应该把隔离子依赖问题直接提升为主仓 P0，除非有明确影响链路。
