# 使用指南：按论文生命周期查阅

本文档按**论文全生命周期 SOP** 组织。

如果你不知道自己现在该读哪一章，先对照下面的时间线：

| 阶段 | 你正在做什么 | 该读哪一章 | 这一章帮你解决什么 |
| --- | --- | --- | --- |
| **Phase 0：选题前** | 还在想做什么方向、范式纠结 | 写作前的顶层设计：研究范式对齐 | 避免"范式不自洽"导致论文被拒，确认自己属于实证/解释/批判中的哪一种 |
| **Phase 1：构思期** | Idea 有了但还没动手，或刚开始搭原型 | 如何讲一个好故事与快速实现 | 学会讲 Motivation、提炼 Insight、用 MVP 快速验证想法 |
| **Phase 2：写作期（核心阶段）** | 要开始正式写论文，不知道从哪下笔 | 论文写作的"由内而外"工作流 | 7 步法：从 Method 开始，由内而外层层包装，避免反复返工 |
| **Phase 3：实验执行期** | 要跑大规模实验、调参、整理数据 | 实验工程防坑指南：并发调度、自动化流与成本控制 | 并行化跑实验、脚本化分析结果、小规模先验证、控制 API 成本 |
| **Phase 4：边界阐述** | 开始写 Limitation 和 Future Work 章节 | Limitation 的写作艺术：直面不足，但要会包装 | 不要把 Limitation 写成忏悔录；学会边界声明 + Contribution 对冲 |
| **Phase 5：压缩定稿期** | 论文写完但超页了、或要控制信息密度 | 如何在有限页数内讲好核心故事 | 按超页严重程度分级压缩：附录迁移、图注置换、孤儿词优化 |
| **Phase 6：投稿拆分期** | 需要将正文和附录拆成两个 PDF 上传 | 正文与附录的拆分提交策略 | 掌握 `xr` 宏包的专业拆分法，交叉引用不失效 |
| **Phase 7：开源发布期** | 双盲投稿时要放代码链接，或论文接收后要开源 | 代码匿名与开源 | 脱敏清洗、匿名平台配置、README 规范、投稿 vs 开源的两套逻辑 |
| **Phase 8：审稿反馈期** | 收到 Rebuttal、准备 Camera Ready | Rebuttal 到 Camera Ready：如何优雅地兑现承诺 | 轻改正文 + 重补附录 + Ref Hook，兑现 Rebuttal 承诺不翻车 |

> **💡 使用建议**：
> 
> - **新人第一次投稿**：建议按顺序通读 Phase 0 → Phase 8，建立全局认知。
> - **老手有针对性查阅**：直接跳到当前阶段对应的章节即可。
> - **卡住不知道该读哪**：看"你正在做什么"那一列，对号入座。
> - **作为 RAG 知识库使用**：本文档结构化程度高（清晰的章节层级、时间线、Table、对比清单），非常适合作为 RAG（检索增强生成）的知识源。建议操作：
>     - **喂给 Cursor / Claude / GPT 作为长期上下文**：写作时让 AI 按本文档的规范给你生成 Method 草稿、Rebuttal 回复、Abstract 等。
>     - **建 Obsidian / Notion 知识库**：把本文档拆分导入，利用 AI 插件（Smart Connections、Notion AI）做语义检索，写论文时现查现用。
>     - **Prompt 示例**：`"根据 [粘贴相关章节]，帮我重写这段 Limitation 段落，并给出改进原因说明"`，比让 AI 凭空发挥可靠得多。

# 写作前的顶层设计：研究范式对齐

[研究范式的宏观概述](https://mp.weixin.qq.com/s/x_5zTKAjwm6VBPF4a_bXSg?scene=1&click_id=45)

[研究范式应用例子](https://mp.weixin.qq.com/s/JcF1PWcfVL414xnah-I6lg?clicktag=bar_share&scene=21&clickpos=0&from_safari=0#wechat_redirect)

在开始“讲故事”之前，必须先检查你的**研究范式** 。

很多论文被拒，不是因为数据不好或文笔差，而是**范式不自洽**：你用 A 范式的逻辑提问，却用 B 范式的方法验证，最后得出了 C 范式的结论。

## 什么是研究范式？

它不是具体的实验方法，而是你“戴着什么眼镜看世界”。

在 科研探索，我们通常面临三种选择，**请在开题/写作前确认你属于哪一种**：

### 实证主义 (Positivism)   "我追求客观真相"

- **核心信念**：世界是可以被测量和还原的。
- **你的问题**：我的 Multi-Agent 系统在模拟舆情时，预测准确率（Accuracy）是否显著高于 Baseline？
- **方法**：大规模定量实验、Ablation Study、SOTA 对比。
- **结果**：**“效果判断型”**（显著提升了 X%）。
- **适用**：大多数 AI 性能优化、算法改进论文。

### 建构/解释主义 (Constructivism)  "我理解复杂机制"

- **核心信念**：关键不是“赢过谁”，而是理解“为什么会这样”。
- **你的问题**：Agent 在交互过程中，是如何产生“盲目跟风”行为的？它的内在推理链条（CoT）发生了什么变化？
- **方法**：Case Study、行为模式分析、可视化分析、用户访谈。
- **结果**：**“机制理解型”**（揭示了 Y 现象背后的 Z 模式）。
- **适用**：HCI（人机交互）、可解释性 AI (XAI)、社会模拟论文。

### 批判/变革范式 (Critical)  "我挑战现有秩序"

- **核心信念**：技术不是中立的，我要揭示它带来的偏见或风险。
- **你的问题**：当前的舆情模拟系统是否会放大特定群体的声音，而掩盖弱势群体的观点？
- **方法**：偏差测试 (Bias Testing)、公平性评估 (Fairness Eval)、伦理审查。
- **结果**：**“规范判断型”**（指出了系统的潜在风险并提出修正）。
- **适用**：AI Ethics（伦理）、AI Safety（安全）、Algorithmic Fairness（公平性）论文。

## 结论

**没有哪种范式更高级，关键是“自洽” (Consistency)。**

如果你做的是 **实证主义** 的论文（为了刷 SOTA），就不要花大量篇幅去写 **批判范式** 的空话（为了人类和平）；

如果你做的是 **解释主义** 的论文（为了探究 Agent 心理），就不要纠结为什么 Accuracy 没有超过 GPT-4。

**一旦范式对齐，你的 Story 就会突然变得稳固、可信。**

# 如何讲一个好故事与快速实现

[参考资料: 科研能力是指什么能力](https://www.zhihu.com/question/60042037/answer/3601970421)

**讲故事**，通过逻辑推演，让听众相信你的 Work 不仅是“新的”(Novel)，而且是“解决痛点必须的”

**快速实现**，通过最小成本，验证你的 idea 真的能跑出“符合直觉又超越直觉”的结果。

## 讲故事不是写说明书

### **❌ 常见误区：把“讲故事”当成“读说明书”**

很多同学一上来就进入“骑脸输出”模式：

> “我的题目是《基于多智能体协同的社交网络舆情演化模拟》。大家看，这是我的系统架构图。我有五个 Agent：一个发帖的，一个评论的，一个审核的……这是我的 Prompt 模板，用了 Chain-of-Thought……”
> 
- **后果**：这是糟糕透顶的讲法。这叫“说明书”，不叫“故事”。你只是在罗列你做了什么，但听众（审稿人）**还没明白为什么要这么做。我不理解你的“Why”，就不可能认同你的“How”。**

### **✅ 正确方法：讲好 Motivation (动机)**

一个清楚的故事，必须在前五分钟回答清楚两个本质问题，直到听众觉得“哟，有点意思！”：

1. **痛点 (The Problem)**：
    - 现有的舆情分析方法（比如传统的 BERT 情感分类、话题聚类）有什么**致命缺陷**？
    - *例子*：“传统方法是静态的，只能分析‘由于’，无法推演‘将要’。它们忽略了舆情传播中最重要的‘人与人交互’（Social Interaction）和‘观点极化’（Polarization）过程。”
2. **关键点 (The Key Idea)**：
    - 为什么要用 **Multi-Agent**？它相比传统 NLP 模型，有什么神奇的特质能解决上面的痛点？
    - *例子*：“因为 Agent 具备角色扮演能力，它能模拟真实的‘乌合之众’心理。只有通过 Agent 之间的动态博弈，我们才能捕捉到舆情反转的关键节点。这是传统静态模型做不到的。”

### **✅ 核心升华：提炼 Insights**

你的 Contribution 不是你用了 GPT-4，也不是你用 LangChain 搭了个系统，那些是皮囊。

- **灵魂拷问**：你的系统模拟效果好，是因为 Multi-Agent 机制本身起作用了，还是单纯因为 GPT-4 的零样本推理能力太强？如果是后者，那我直接问 GPT-4 不就行了，要你的系统干嘛？
- **Insight 提炼**：我们必须解释清楚：**为了让 Agent 模拟出真实的人类非理性行为，做了什么独特的设计？**
    - *Insight 例子*：“我们发现简单的 Agent 交互会导致‘盲目跟风’（Sycophancy）。我们的贡献在于设计了一种‘私有内心独白’（Inner Monologue）机制，强迫 Agent 在公开表态前先进行自我反思，这才是模拟出真实舆情反转的关键。”    **这才是可以传承的 Insight。**

## 如何讲一个好故事

“讲故事”本质上是一“逻辑闭环的构建能力”。

它要求我们从**“做题家”思维**（我做了什么）转变为**“推销员”思维（你为什么需要这个）**

> **⚠️ 双受众意识**：
> 
> 
> 本章所有“讲故事”的技巧，都是面向**论文投稿**场景
> 
> 你要说服的是**审稿人**，他们需要被你的逻辑打动，而通常不会真正去 clone 你的仓库跑代码。
> 
> 但你的 GitHub 开源仓库面向的是完全不同的受众：那些真正会复现你的实验、cite 你的论文、在你的工作基础上继续构建的**同行研究者**。
> 
> 论文要“说服判断者”，开源要“服务使用者”
> 
> 两者的写作侧重点截然不同。
> 

### 1. 定义战场 (Context)

- **做什么**：用一句话定义大背景。
- *例子*：“网络舆情治理的核心，在于提前预判谣言的传播路径。”

### 2. 制造冲突 (Motivation - The "Gap")

- **痛点 (Pain)**：现有方案（静态 NLP）无法处理动态交互，无法预测“蝴蝶效应”。
- **关键点 (Intuition)**：Multi-Agent 系统天然适合模拟社会交互，因为它能还原“人”的社交属性。

### 3. 展示武器 (Method - The "How")

- **做什么**：展示具体设计。
- **标准**：不要堆砌 Prompt 细节，重点讲 Agent 之间的**交互拓扑结构**和**记忆更新机制**。

### 4. 升华价值 (Contribution - The "Insight")

- **核心逻辑**：Contribution = **新知识**，而不仅仅是**新系统**。
- *例子*：不要只说“我的模拟准确率提升了 10%”。要说“我们揭示了舆情反转的一个临界点：当持有‘沉默螺旋’心理的 Agent 比例低于 30% 时，谣言辟谣才会生效。这是我们系统的核心发现。”

## 快速实现

在系统与 AI 应用领域，这个能力甚至比讲故事更关键（70分 vs 90分）。

核心是用**最少的时间精力**设计实现一个**最精简的原型系统**，以科学验证核心想法。

### **❌ 常见错误：**

1. **过度设计，过早优化**：
    - *例子*：还没跑通最基本的对话逻辑，就开始担心“如果有 100 万个 Agent 并发怎么办？”、“要不要上 Kafka 做消息队列？”、“数据库选 Neo4j 还是 MySQL？”
    - *评语*：这是“怪力乱神”，纯属浪费时间。先跑通 10 个 Agent 再说。
2. **不聚焦，乱开线程**：
    - *例子*：为了做舆情分析，发现没有现成的数据，于是花了两周去写推特/微博的爬虫，研究反爬策略。
    - *评语*：博士生不是爬虫工程师。你的研究核心是 Agent 交互，不是数据获取。**马上停下来**，去找开源数据集（如 Kaggle），或者手动造 50 条假数据先跑起来。
3. **对比实验不科学**：
    - 引入了太多变量（换了模型，又换了 Prompt，还换了数据），最后说效果好了，根本不知道是谁的功劳。

### **✅ 正确路径：MVP (Minimum Viable Prototype)**

- **糙但有用**：放弃前端界面（用 Print 就行），放弃数据库（用 CSV 就行），放弃复杂的调度框架（写个 Python Loop 就行）。
- **核心优先**：只实现那个“私有内心独白”的机制，其他的都可以 Hard-code。
- **单线程工作**：遇到工程障碍（比如某个 Agent 框架报错），如果修不好，马上换一个最简单的实现方式，不要死磕框架源码。

## 进阶解析

### Motivation vs. Insight

很多同学容易把“我想到了用 Agent”误认为是 Insight。这是错误的。

| 维度 | Motivation (做之前的假设) | Insight (做之后的结晶) |
| --- | --- | --- |
| **例子** | “Agent 能模拟人类，比静态模型好，所以我要用它。” | “我们发现 Agent 之间如果沟通太频繁，会导致观点同质化（Information Cocoon）。**必须引入‘信息遗忘机制’才能打破回音室效应。这个发现才是 Insight。**” |
| **深度** | **浅显、宏观、直觉性** | **具体、微观、经验性** |

### 怎样算“最小原型” (MVP)？

针对“多 Agent 系统工作量巨大”的困惑：

- **定义**：一个能**跑通核心流程**、且能**产出对比数据**的最小代码集合。
- **操作**：
    1. **Step 1 (验证期)**：不要写 Web 界面！不要接真实微博 API！手写 20 个用户人设，让它们在一个 list 里循环对话。看看能不能涌现出预期的“舆情反转”。
    2. **Step 2 (决策期)**：
        - 如果有有趣的现象涌现 -> 继续完善，接真实数据。
        - 如果 Agent 只是在复读 -> 马上检查 Prompt 或交互逻辑，或者放弃这个 Idea。
    3. **Step 3 (开发期)**：确定 Idea 能打之后，再考虑用什么数据库和前端展示。

# 论文写作的"由内而外"工作流

很多同学一上来写论文就死磕 Introduction，花了三天憋出 10 句话，结果后面 Method 改了一下，Intro 又要全部重写。

**这是典型的"由外而内"写法，用还没确定的骨架去撑起最华丽的门面**，注定返工。

正确的思路是"由内而外"：先把最硬核、最不容易变的部分（Method、Experiment）敲定，再一层一层往外包装（Intro、Related Work、Abstract）。

你把"内核"焊死了，"外壳"怎么写都不跑偏。

## 写作顺序：7 步法

以下是推荐的落笔顺序，**从内到外、从实到虚**：

```
[前置] 轻量文献扫描       ← 避免做重复工作，10-20 篇文献快速扫一遍
  ↓
1. 拟定初步方法名 (Working Title)
  ↓
2. Method (草图先行，文字跟进，精图后置)   ← 写完后复盘一次方法名
  ↓
3. Experiment (先出主结果表/图，再写文字)
  ↓
4. Introduction (Motivation + Contribution)
  ↓
5. Related Work (正式成文，精准对位)
  ↓
6. Abstract + Conclusion
  ↓
7. Limitation + Ethic (如果需要)
```

## Step 0：前置文献扫描

**别把文献调研当成 Related Work 章节来做，那是后期才定稿的事。**

前置扫描的目的只有一个：**避免你做完了才发现别人去年已经做过了。**

- **操作**：**直接用 Gemini DeepResearch 多跑几轮**。喂进去你的研究关键词（比如"Multi-Agent 舆情模拟 + 社交网络 + 观点极化"），让它帮你自动扫 10-20 篇最相关的文献，看完摘要和方法图就行。跑 2-3 轮，每轮换一个切入角度（方法视角 / 应用视角 / 对比视角），覆盖面就够了。
- **重点**：不是读透每篇，而是搞清楚三件事：
    1. 我的 Idea 有没有人已经做过？（查重）
    2. 现有方法的共同短板是什么？（找 Gap）
    3. 有哪些 Baseline 可以在后面实验里对比？（搜集弹药）
- **记录方式**：DeepResearch 会直接给你整理好 `[论文名 | 核心方法 | 短板 | 和我的区别]` 这种结构化表格，直接保存下来，后面 Related Work 的素材库就现成了。

> **⚠️ 警告**：不要在这一步陷入"综述式精读"的陷阱。你的目标是"快速建立地图"，不是"成为这个领域的专家"。
> 

## Step 1：拟定初步方法名（Working Title）

方法还没写，就先起个名字？**是的，必须先起名。**

起名字这件事逼你做一件事：**用一个词概括你的核心创新是什么**。

- 如果你起不出来名字，说明你的 Idea 还没聚焦。
- 如果你能起出 EvoCorps, `AgentMark` 这种两三个词的名字，说明你知道自己在做什么。

### 先起一个"工作名"就行，丑点没关系

这个阶段的名字叫 **Working Title（临时名称）**，意思是"先用着，后面可能要改"。

- *例子*：你做了一个让 Agent 先自我反思再发言的机制，初期可以叫 `SelfReflectAgent`（很土，但能用）。
- *后期演化*：Method 写完后，发现核心其实是"内心独白"，改名为 `Inner Monologue`（立刻高级）。

### 方法名需要复盘一次

**Method 章节写完后，请停下来问自己一句：这个名字还合适吗？**

很多时候 Working Title 是基于"我打算做什么"，而 Method 成型后你会发现"我真正做成了什么"和最初的预期有偏差。这时就需要更名。

- **更名操作很简单**：用 **全局替换**功能一键搞定（VSCode / Overleaf 都支持）。
- **注意**：替换前先检查有没有同名的专有词汇（比如你用 `Agent` 这种通用词命名，全局替换会炸）。

> **一句话**：方法名不是一次定终身，而是"先占位、后美化"。别在起名上纠结超过 5 分钟。
> 

## Step 2：Method（草图先行，精图后置）

Method 是整篇论文最硬的骨头，先把它敲定，后面一切都稳。

### 核心约定：草图先行，精图后置

很多人在"先画图"还是"先写字"之间反复横跳，其实**最优解是把"图"拆成两个阶段**：草图（用来思考）和精图（用来投稿）。

- **草图成本极低**（5-10 分钟），用来**锚定你的方法逻辑**，防止文字越写越绕。
- **精图成本极高**（可能要半天到一天），**必须等文字稳定后再做**，否则反复返工让你崩溃。

理由很直接：

- 草图画不出来 = 你的方法逻辑还没理清，硬写文字只会写一堆缠绕不清的废话。
- 文字没定稿就上精图 = 你会在 TikZ 和 Figma 里反复返工，心态爆炸。

### 操作步骤

1. **先画一张草图 (Sketch)**：**纸笔、白板、PPT、draw.io 都行**，10-30 分钟搞定，不追求美观，能说明白逻辑即可。这张草图至少要讲清楚三件事：
    - **Elements（构成元素）**：系统里有哪些模块？每个模块是什么角色？（例如：User Agent、Moderator Agent、Memory Module、Retriever……）
        - **Data Flow（数据流向）**：数据从哪里出发，经过哪些模块加工，被谁消费？用**箭头**标明流向，避免"谁连谁"含糊不清。
        - **I/O（输入输出）**：整个系统的输入是什么（User Query / Raw Tweets / ...）？输出是什么（Prediction / Dialogue / Ranking / ...）？**输入输出必须画在图的两端**，让读者一眼看清起点和终点。
    - *作用*：给你的 Method 打骨架，同时可以早期发给导师/合作者对齐方向。
    - *自检标准*：把草图给一个不了解你课题的同学看，他如果能复述出"输入 → 流程 → 输出"，说明草图合格；如果他问"这个箭头是什么意思？"，说明你还没画清楚。
2. **围绕草图写 Method 正文**：按模块顺序逐一展开。每个模块回答三个问题：
    - 这个模块做什么？（功能）
        - 它是怎么做的？（机制）
        - 为什么这么设计？（动机）
3. **文字写着写着发现草图有问题**：果断改草图。草图成本低，这时候改不心疼。
4. **文字稳定后，再做精图**：**强烈推荐用 PPT 直接画**，升级成投稿级质量。
    - *为什么是 PPT*：一图多用。同一张图日后你还要拿去组会汇报、会议 Oral、开题答辩、保研求职。**PPT 里的矢量图形可以无损复用**，别的工具 导出到 PPT 还会失真。
        - *投稿导出*：画完后用"另存为 PDF"→ 裁剪成单页 → 直接 `\includegraphics` 到 LaTeX 里，清晰度完全够顶会标准。
        - *小技巧*：字体统一用 Times New Roman ；线条粗细、箭头样式保持一致；配色用色卡套件，避免花里胡哨。

> **⚠️ 关键红线**：**没有文字稳定前，绝对不要做精图。** 有些人喜欢早期就上精图一把梭，结果方法改了两次，图画了五版，三天时间全耗在调线条上了。
> 

### 例外：可以直接"先写字"的情况

有三种情况你可以跳过草图，直接写文字：

1. **方法逻辑非常简单**：比如就是 "Algorithm A + Loss B"，一句话能说清的不需要画图辅助思考。
2. **你已经在脑子里画过 10 遍了**：方法想得非常清楚，不需要外化成草图。
3. **方法还在剧烈迭代**：你知道下周可能要大改，这时候画图就是给自己找罪受。

但即使是上述情况，**最终投稿版必须有一张精图**——这是审稿人第一眼看的东西，没有图几乎等于自动扣分。

### 写完后的自检

Method 写完后，**立刻回去看 Working Title 还合不合适**。如果你的核心机制在 Method 里的描述和名字有出入，果断改名。

## Step 3：Experiment（先出主结果，再写分析）

同样遵循"先搭骨架、再写分析"的原则，但这里是 **"Tables First"**（表格先行）。

### 操作步骤

1. **先把主结果表画出来**：横轴是什么方法/模型，纵轴是什么指标，表格填满数字。**哪怕数字还没跑完，先把表格骨架搭好**。
2. **围绕表格写分析文字**：
    - Table X 展示了什么？
        - 你的方法赢在哪里？输在哪里？
        - 为什么赢/输？（这里就是 Insight 的生产车间）
3. **Ablation Study 的表最后出**：主结果稳了，再来做消融。

### 避免常见坑

- **跑实验的时间别浪费，可以并行写 Method / Related Work**：实验跑起来经常是几小时到几天，这时候 **CPU/GPU 在忙，你的脑子没在忙**，完全可以并行推进 Method 章节、Related Work 或者图表美化，这是合理的时间管理。
- **⚠️ 但绝对不能"脑测"写 Experiment 的分析**：没有真实数据就硬写 Experiment 的分析段落（比如"我们的方法在 XXX 上提升了 X%"，数字纯靠拍脑袋），这是自杀式操作。理由有二：
    1. 数字一旦出来和你猜的不一样**（大概率会），你前面写的所有"叙事逻辑"都要推翻重写。
    2. Insight 只能从真实数据里长出来。你脑补的"我们方法赢在 XXX"经常是错的，真实赢点可能是另一个维度，只有看到数据才能发现。
- **别按时间顺序记流水账**：论文不是实验日志。正文里应该是"精心编排后的叙事顺序"，而不是"我先做了 A，然后做了 B"。
    - **本质上：论文是在兜售你的科研 Idea，实验结果是为 Idea 服务的"论据"，不是主角。**
    - *类比*：看看每次大模型发布（GPT、Claude、Gemini、DeepSeek……），官方博客里永远是**精选对自己有利的 benchmark** 做展示：推理强就放 AIME、GPQA；代码强就放 SWE-Bench、LiveCodeBench；长文本强就放 Needle-in-a-Haystack。**没人会把所有跑过的榜单一股脑糊上来**，更不会按"我先跑了 A 榜，再跑了 B 榜"的时间线叙述。
    - *落到你身上*：主结果 Table 放能 support 你核心 Claim 的实验；Ablation 放能**反证你设计有效**的对照；Case Study 放最能**可视化你 Insight** 的例子。**跑过但无用的实验，该扔进附录就扔附录，该删就删，别心疼。**

> **一句话原则**：**手可以先写、脑不能瞎猜**。Method 和 Related Work 可以边跑边写，Experiment 的分析必须等数据出来再动笔。
> 

## Step 4：Introduction（核心确定， 再来包装故事）

**Method 和 Experiment 都定稿了，这时候再写 Introduction，你会发现无比顺手。**

因为你已经知道：

- 你的核心贡献到底是什么（Method 告诉你）
- 你的数字能打到什么程度（Experiment 告诉你）
- 所以你在 Intro 里的每一句"We propose..."、"Our method achieves..." 都有底气。

### ⚠️ 警告：Intro 虽然几乎最后写，但它才是决定生死的一环

很多人以为"Intro 写在最后 = Intro 不重要"。这是个要命的误解。

**审稿人打开你的论文，第一眼看的就是 Intro。**

**前 1-2 页没抓住他，后面 Method 写得再精妙他也懒得看。**

> **一句话残酷事实**：Method 和 Experiment 决定你"值不值得发"，但 Intro 决定审稿人"愿不愿意认真读"。
> 

### **Intro 不是"介绍"，是"推销"**

论文投稿本质上就是**把"论文"这个科研产物，卖给那几个审稿人**。

你要让 3-5 个陌生人，在几十分钟内相信你的工作值得被顶会接收。

这就是一场彻头彻尾的"ToB 销售"，目标客户是审稿人，产品是你的 Idea，成交标准是 Accept。

既然本质是卖货，那就**把论文当商品详情页来打磨**：Intro 就是你这款产品的**详情页头图 + 卖点海报**。

| 论文结构 | 对应电商逻辑 | 职责 |
| --- | --- | --- |
| **Title + Abstract** | 商品主图 + 一句话文案 | 让人在搜索结果里**愿意点进来** |
| **Introduction** | 详情页头图 + 卖点海报 | 让人点进来后**愿意往下滑** |
| **Method** | 产品参数规格表 | 给专业买家看的**技术背书** |
| **Experiment** | 用户评价 + 实测对比图 | 用**客观数据**证明产品确实好 |
| **Conclusion** | "立即购买"按钮 + 复购引导 | 让人**记住这个牌子**并回来 |

这个类比最关键的启示：

- **Method 再牛，没有 Intro 的卖点提炼，就是堆在仓库里的好货，没人看得到。**
- **Intro 不是"介绍文章"，是在"兜售你的 Idea"。** 你要像电商文案一样，三秒内让读者明白："这玩意儿能解决我什么痛点 + 为什么值得我花时间读"。

### 卖货式 Intro 的经典 4 段式

按 **"如何讲一个好故事"** 那一章的公式走，对应到卖货逻辑：

1. **定义战场 (Context)**：一段话定背景。
    - *卖货对应*：**"你是不是也遇到过这个问题？"** —— 唤起用户的痛点认知。
2. **制造冲突 (Motivation)**：现有方法怎么做的，Gap 在哪？
    - *卖货对应*：**"市面上现有的方案都不行，因为……"** —— 基于同行的不足来抬自己（**学术论文里要有分寸，点到为止**）。
3. **展示武器 (Method Overview)**：我们提出了 `[你的方法名]`，它通过 XXX 来解决这个问题。
    - *卖货对应*：**"我们推出的新产品，核心黑科技是……"** —— 一句话讲清独特卖点（USP）。
4. **升华价值 (Contribution)**：列 3 条核心贡献。
    - *卖货对应*：**"买了这款，你能获得 1、2、3……"** —— 直接摆出价值，不藏着掖着。

### 常见误区：把 Intro 写成"学术综述"

**❌ 典型烂 Intro**（综述式）：

> "Deep learning has achieved great success in NLP. Many works [A, B, C, D, E] have been proposed. Some focus on X, others on Y... In this paper, we also propose a method..."
> 

这不是 Intro，这是"我读过的论文大全"。审稿人看完只会记住"又一个方法"。

**✅ 卖货式 Intro**（痛点 + 方案）：

> "Simulating opinion polarization in social networks is crucial for rumor prevention, yet existing NLP-based methods fail to capture the dynamic, agent-to-agent nature of opinion formation. **We propose `Inner Monologue`**, a multi-agent framework that... Our method reveals a critical tipping point: when agents with 'spiral of silence' psychology drop below 30%, rumor-debunking becomes effective."
> 

审稿人读完立刻明白：**痛点是什么 + 你怎么解决 + 你发现了什么新东西**。

> **💡 核心原则**：**Intro 不是最后写就等于最后重要，它往往是审稿人唯一会认真读的部分。** 请用打磨卖点文案的心态打磨你的 Intro，每一句话都要有销售力。
> 

## Step 5：Related Work（精准对位，不是流水账）

前置扫描时积累的那张文献表，现在派上用场了。

### Related Work 不是"我读过的书单"

很多人写 Related Work 就是流水账：`[作者A] 做了 X；[作者B] 做了 Y；[作者C] 做了 Z……`

**这种写法等于告诉审稿人："我读了一堆东西，但我不知道它们和我有什么关系。"**

### 正确写法：按主题分块 + 明确定位

1. **按主题分块**：把前置扫描表里的文献，按 2-3 个主题归类。比如：
    - Theme 1：Agent 架构的研究
    - Theme 2：舆情模拟的传统方法
    - Theme 3：多智能体协同机制
2. **每块末尾明确定位**：写一句话说明"这些工作和我们的区别是什么"。
    - *例子*：`While these methods focus on X, our approach uniquely addresses Y by introducing [方法名].`
3. **正式成文放 Intro 之后**：这时你已经知道自己的贡献是什么，写起来才能精准对位，而不是泛泛而谈。

## Step 6：Abstract + Conclusion（最后浓缩）

**全文定稿后，才能写 Abstract 和 Conclusion。**

这两部分是"最浓缩的卖点"，写早了等于在卖一个还没造出来的产品，永远在返工。

### Abstract 的经典 5 句式

1. **背景**：这个领域面临什么问题？（1 句）
2. **Gap**：现有方法的不足是什么？（1 句）
3. **Method**：我们提出了 `[方法名]`，它通过 XXX 来解决。（1-2 句）
4. **Result**：在 XXX 数据集上，我们达到了 XXX 性能。（1 句）
5. **Insight**：我们的工作揭示了 XXX。（1 句，可选）

### Conclusion 不等于 Abstract 的复制粘贴

- **Abstract**：写给**没读过论文**的人看，让他决定要不要读。
- **Conclusion**：写给**读完论文**的人看，帮他总结"他读到了什么 + 下一步该往哪走"。

> **差异**：Conclusion 里可以适度展望 Future Work 和 Limitation 的对冲方向，Abstract 里则不必。
> 

### ⚠️ 特殊情况：Abstract Deadline 早于正文 Deadline

部分顶会（如 NeurIPS、ICML 等）采用 **两阶段截稿** 机制：**先交 Abstract，过一两周再交完整论文**。这时候 Abstract 没法等全文定稿才动笔。

- **理想情况**：如果你节奏够快，正文已经八九不离十，那就按前面的 5 句式认真写一版。
- **现实情况**：正文还在赶，这时候请允许自己写一个"占位版 Abstract"，基于以下四个要素快速拼出一版：
    1. **背景**（你要解决的大问题是什么）
    2. **挑战**（现有方法的 Gap 是什么）
    3. **创新点**（你打算怎么解决，方法名是什么）
    4. **预期效果**（大致的性能提升方向，哪怕还没跑完最终数字）

> **别焦虑**：虽然大家都说"Abstract 别大改"，但实际上两阶段截稿之间你**完全可以修改 Abstract**，审稿系统也允许覆盖提交。只要核心的方法名、Motivation 和 Contribution 的大方向不变，最终 Abstract 和提交版略有出入，审稿人根本不会纠结这一点。
> 
> 
> **重点是**：先占位拿到投稿资格，再优化细节。**错过 Abstract Deadline = 直接失去投稿资格**，这比写得不完美严重一百倍。
> 

## Step 7：Limitation + Ethic（压轴，不是废话）

Limitation 为什么最后写？**因为只有看到全文的最终呈现，你才能客观判断"哪些是真短板、哪些可以包装成研究边界"。**

具体怎么写，请参考下一章 **"Limitation 的写作艺术：直面不足，但要会包装"**。

Ethic 章节不是所有会议都要，但只要涉及到用户数据、社会影响、生成有害内容等主题，**哪怕会议不要求，也建议主动加一段**，这会让审稿人觉得你是个有责任感的研究者。

## 总结

| 传统写法（由外而内） | 推荐写法（由内而外） |
| --- | --- |
| 先写 Intro，憋半天写不出 | 先锁定 Method，Intro 水到渠成 |
| 边跑实验边写 Experiment | 实验稳了再写，叙事顺序可精心编排 |
| Related Work 写成读书笔记 | Related Work 精准对位自己的贡献 |
| Abstract 写了改、改了写 | 最后一蹴而就 |

**一句话记住：写论文最好不要从封面写到封底，而是从最硬的 Method 向外辐射。**

# **Limitation 的写作艺术：直面不足，但要会包装**

Limitation 是论文中最微妙的章节。写多了是自杀，写少了是找死，不写是作死。

## **写作心理：为什么很多人把 Limitation 写崩了？**

很多同学（尤其是让 AI 代写的）会犯一个致命错误：**把 Limitation 写成忏悔录**。

> “我们的方法没有考虑多语言场景……也没有在更大规模的数据集上验证……模型的可解释性也不够……此外，计算开销较大……而且我们只测试了 GPT-4，没有测试开源模型……”
> 

写完之后还觉得自己很诚恳，觉得审稿人一定会被这份**“学术谦逊”**感动。

**不会的。审稿人看完只会想一件事：既然你的方法有这么多不足，那它的价值在哪里？你的 Method 是不是太烂了？**

这就是 Limitation 写作的核心悖论：

- 你以为在“诚实”，审稿人觉得你在“自证无能”。
- 你以为在“摘清责任”，审稿人觉得你“连自己的贡献都不自信”。

## **正确心态：辩证看待，而不是自我否定**

先搞清楚一个前提：

**如果你的方法完全没有价值，你不会投这个顶会；**

**如果你的方法完全没有 Limitation，那我建议你别读研了——请直接去创业。**

世界上没有十全十美的方法。Transformer 刚出来的时候计算开销巨大；BERT 不能做生成；GPT-2 会生成有害内容。但这些 Limitation 丝毫不影响它们成为里程碑式的工作。

**很多伟大的成果，都是开始于一个微末的、有明显局限的原型。**

所以 Limitation 的写作心态不是“自我鞭笞”，而是：

> **“我清楚地知道边界在哪里，但我的核心贡献在这个边界内是扎实的。”**
> 

## **为什么必须包装？**

两个原因：

1. **审稿人是专家，不是圣人**
    
    所谓顶会，是顶级研究者会投的会议，里面的审稿人是科研领域人精中的人精、专家中的专家。即使现在 AI 导致审稿人群体整体良莠不齐，但请不要去赌这件事。
    
    你的 Limitation 中任何一条“致命伤”，都可能成为审稿人拒稿的理由。**裸露的弱点 = 递给对方的子弹。**
    
2. **Limitation ≠ 缺陷清单，而是研究边界声明**
    
    好的 Limitation 不是在说“我做得不好”，而是在说“在这个范围内我做得很好，超出这个范围需要后续工作”。这是两种完全不同的叙事框架
    
    前者让人觉得你的工作不成熟，后者让人觉得你的工作有清晰的边界意识和发展潜力。
    

## **怎么包装？核心技巧**

### **原则一：一段足矣，克制篇幅**

Limitation 通常放在 Discussion 或 Conclusion 的末尾，**一段话（5-8句）足够**。写太多等于在告诉审稿人“我的方法浑身是洞”。

### **原则二：不要回避主要不足，但要辩证阐述**

默认顶会审稿人能看出你方法的核心短板。如果你故意不提，他们会在 Review 里写：“The authors fail to discuss the obvious limitation of...”

这比你自己写出来更致命，因为它暗示你**要么没意识到，要么在刻意隐瞒**。

正确做法是**直面，但立刻用 Contribution 对冲**：

- **❌ 裸露写法**：“Our method has high computational cost, which limits its practical deployment.”
→ 审稿人内心：“那你这方法有什么用？”
- **✅ 包装写法**：“While our method incurs higher computational cost compared to static baselines, this overhead is inherent to the dynamic agent interaction paradigm that enables our core contribution, capturing opinion reversal patterns that static methods fundamentally cannot model. We believe this trade-off is justified, and future work on agent pruning and asynchronous interaction can further reduce the cost.”
→ 审稿人内心：“嗯，合理，这个 cost 是为了换核心能力，而且他有优化方向。”

### **原则三：把 Limitation 转化为 Future Work 的跳板**

每一条 Limitation 后面都应该紧跟一个“但是我们已经知道怎么改进”的暗示。这不是在承认失败，而是在向审稿人展示：**你对自己研究的掌控力远超论文本身。**

| **❌ 自杀式写法** | **✅ 包装式写法** |
| --- | --- |
| “We only tested on English data.” | “Our current evaluation focuses on English corpora. Extending to multilingual settings is a promising direction, as our agent architecture is language-agnostic by design.” |
| “We did not compare with Method X.” | “Due to the fundamentally different problem formulation, direct comparison with Method X is non-trivial; we leave the design of a fair cross-paradigm benchmark to future work.” |
| “The model lacks interpretability.” | “While the emergent behaviors are not yet fully interpretable, our Inner Monologue mechanism (Sec. 3.2) provides a first step toward traceable agent reasoning, which we plan to formalize in future work.” |

### **原则四：Limitation 的选择本身就是一种策略**

你不需要列出所有不足，**只需要选择那些你能“接住”的**。所谓“接住”，就是你能给出合理的解释或明确的改进方向。那些你完全无法辩护的致命缺陷，如果审稿人没提，你也不需要主动递刀。

> **底线**：不能撒谎，不能隐瞒审稿人大概率会发现的显著问题。但在这个底线之上，你有权选择“展示哪些边界”。
> 

### **总结：Limitation 的写作公式**

> **承认边界 → 归因于研究范式选择（而非方法缺陷） → 用 Contribution 对冲 → 指向 Future Work**
> 

一个好的 Limitation 段落读完后，审稿人应该觉得：“这个方法确实有局限，但作者很清醒，核心贡献是站得住的，而且改进方向很明确。” 而不是：“这方法一堆毛病，作者自己都承认了。”

# 如何在有限页数内讲好核心故事

写论文时，**“篇幅限制”** 往往是我们最大的敌人，也是最好的朋友。

它逼迫我们剔除冗余，只保留最精华的思考。

不要为了压缩而压缩，我们的目标是：

**在保障论文核心逻辑清晰和可复现的基础上，最大化提高信息密度**

> **⚠️ 与开源的反向关系**
> 
> 
> 本章讨论的所有压缩与精简策略，专门服务于论文的页数限制。
> 
> 但请记住，你在论文中“砍掉”的实现细节、超参设置和完整 Prompt，在后续 GitHub 开源时必须**全部补回来**
> 
> 因为开源面向的是真正要复现你工作的同行，他们需要的不是精炼的故事，而是完整的技术蓝图。
> 

## 图表与排版

图表是论文的“门面”，但也最占空间。原则是 “不要让读者为了看一个简单的数字而翻页”。

### 多表合一

不要把相关的实验拆成两张表。

只要行（Rows）或列（Columns）有重叠，就应该合并。

- **建议**：如果 Table 1 比较不同模型的 Accuracy，Table 2 比较它们的 Efficiency，且模型列表是一样的，请把它们合并成一个表。
- **技巧**：利用 `\multirow` 和 `\multicolumn`，共用表头（Header）可以节省大量重复的垂直空间。

### 利用图注空间

图注（Caption）不仅仅是给图片起个名字，它是正文之外的**第二战场**。利用好它，可以把正文的行数省下来讲“故事”。

**核心判决标准：**

- **放进 `Experimental Settings` (正文) 的**：必须是**全局通用**的、关乎**核心复现**的、或者**所有实验公用**的设置（例如数据集介绍、评测指标的数学定义、主干网络结构、全篇通用的超参）。
- **放进 `Caption` (图注) 的**：必须是**仅针对这一张图**有效的、或者**辅助阅读**的视觉信息（例如线条颜色含义、缩写特指、仅此实验特有的微调参数）。

### 情况一：必须写在“正文实验设置”里

如果这个信息缺失了，**整章实验**都看不懂，或者会对**复现**造成重大困扰，必须在正文。

- **数据集划分**：Train/Test split 怎么分的？
- **通用 Metrics**：Accuracy, F1, ASR 的具体公式定义。
- **核心环境**：用了几张 A100，PyTorch 版本（仅针对系统与架构类论文；纯算法论文可以移至附录）
- **Baselines 来源**：对比的算法具体引用自哪篇论文。

### 情况二：强烈建议塞进“图注”里

如果这个信息是为了**解释这张图怎么看**，或者只是**这一小个实验的特例**，可以考虑塞进图注。

1. **视觉解码**
    - *例子*：“The **dashed lines** represent the theoretical upper bound, and the **solid lines** represent our method.”（虚实线的含义）
    - *例子*：“**Blue bars**: accuracy; **Red curve**: latency.”（颜色对应关系）
2. **统计细节**
    - *例子*：“Error bars denote the standard deviation over **5 independent runs with random seeds**.”（不要在正文里反复说跑了5次，图注里提一次就行）
3. **局部缩写或特指**
    - *例子*：“'w/o Attn' denotes the ablation variant removing the Attention module.”（这种缩写解释不需要占正文一行）
4. **次要的实验参数**
    - *例子*：正文里对比了主要性能，图里展示参数敏感度。
    - *Caption*：“Effect of temperature $\tau$. **Here we fix $\alpha=0.5$ and vary**  $\tau$. **from 0.1 to 1.0.**”（这个 $\alpha$ 固定为0.5只针对这张图有效，没必要在正文专门写一句）

### 紧凑布局

- **拒绝“简单图霸屏”**：不要让一张简单的柱状图占满半页。使用 `minipage` 或 `subfig` 将多张小图（如 FPR 曲线和 Robustness 分析）并排展示。
- **裁剪白边**：用 PDF 处理工具裁掉图片周围多余的空白，LaTeX 的 `vspace` 大法虽然好用，但不如源图紧凑来得自然。
- **图例内置**：不要让图例（Legend）单独占图表的一侧。在绘图脚本中将图例设为半透明并悬浮在图表内部的空白区域（如左上角），而非默认的外部排列。
- **图中文字可读性 (Legibility)**：这是审稿红线。**图中的文字大小必须 $\ge$ 正文文字大小。**
    - **在 LaTeX 编译后的 PDF 中检查**。将 PDF 阅读器缩放至 100%，对比图中文字与下方的图注（Caption）文字。如果图中文字明显更小，请回 Python 调整 figsize 和 fontsize，而不是在 LaTeX 里调整图片拉伸。

## 附录与正文的内容分级

论文不是实验记录本，不需要事无巨细。

遵循"冰山原则"：正文是海面上的冰山（核心逻辑与贡献），附录是海面下的基座（复现细节）。

### 附录到底是什么？为什么我们需要它？

很多同学把附录理解为"放不下了才丢过去的垃圾桶"。这是完全错误的。

**附录的本质是：给正文提供"可选的纵深"。**

**正文负责回答**"你做了什么、为什么有效"**（What & Why）**

**附录负责回答**"具体怎么做的、怎么复现"**（How exactly）**

> **类比**：你去听一个 20 分钟的学术报告（= 正文），讲者讲完核心思想和主要结果。
> 
> 
> 然后 Q&A 环节有人问"你那个 Prompt 具体怎么写的？"、"你的 Agent 记忆模块用了多大的 buffer？"
> 
> **这些答案就是附录的内容**。它们重要，但不应该挤进 20 分钟的正文里。
> 

### 常见问题：把实验章节写成 README

这是当前最常见、最致命的写作错误之一。

很多同学（尤其是做 Agent 系统的）写 Experiment 时，不自觉地把论文写成了 GitHub README。

### **❌ README 式写法（像操作手册）**

> 我们首先从“configs/personas/”中存储的个性模板初始化 50 个代理。每个代理都以 GPT-4o-mini 作为基础模型实例化。我们将温度设为 0.7，top_p 设为 0.9，最大生成标记数设为 2048。内存缓冲区大小为 16。我们运行 100 轮模拟。在每一轮中，代理轮流发布、评论并更新其内部状态。日志保存在“results/run_{seed}/”中。我们使用 3 个随机种子（42、123、2024），并报告平均值。
> 

审稿人读完内心：**"所以呢？你告诉我怎么跑代码，但你不告诉我你发现了什么？"**

这段话全是**操作步骤（How to Run）**，没有任何**科学发现（What We Found）**。

**这不是论文，这是部署文档。**

### **✅ 论文式写法（像科学叙事）**

> 我们模拟了一个由 **50 个异质性主体构成的社会网络**，每个主体都具有独特的个性**（见附录 A）**。这些主体通过发布和评论的方式在 **100 轮互动**中进行交流。为了评估我们的自我进化机制是否真正提高了观点的多样性，我们在每一轮都测量了表达观点的熵（EEO）。**如表 1 所示**，在没有自我进化模块的情况下，到第 40 轮时主体们就趋于形成单一的主导观点（EEO 下降到 0.12）。而当启用自我进化功能时，主体们在整个过程中都保持着多样化的视角（EEO 一直保持在 0.65 以上），**这证实了反思性的自我更新循环能够防止“回音室”效应的崩溃。**
> 

审稿人读完这段话接收到的信息是这样的：

> **① “实验设置我懂了”**（50 agents, 100 rounds, Appendix A 放了细节）→ 不需要翻来覆去看超参，核心设定一句话交代完毕。
> 
> 
> **② “他有明确的评估目标”**（EEO 这个指标是用来验证“观点多样性”的）→ 不是乱跑一通再找数字编故事，而是带着 Claim 去验证。
> 
> **③ “有对比，有数字，有结论”**（0.12 vs 0.65，round 40 是临界点）→ 这种精确的数据对比让审稿人觉得实验是扎实的，不是手感描述。
> 
> **④ “核心发现我记住了”**（self-update loop prevents echo chamber collapse）→ 审稿人合上论文后能用一句话概括你的 Insight，这说明你的叙事成功了。
> 

| 维度 | README 式（❌） | 论文式（✅） |
| --- | --- | --- |
| **核心内容** | 怎么跑代码（操作步骤） | 发现了什么（科学结论） |
| **读者获得** | "我知道怎么复现了" | "我知道这个方法为什么有效了" |
| **超参细节** | 全部堆在正文里 | 一句 `(Appendix A)` 带过 |
| **叙事逻辑** | 按执行顺序流水账 | 按 Claim → Evidence → Insight 编排 |
| **审稿人感受** | "这是个工程文档" | "这是一篇有发现的论文" |

### 正文 vs 附录：判定标准

问自己一个问题：**"如果不看这段话，审稿人还能理解我的核心贡献吗？"**

- **能** → 移到附录。
- **不能** → 留在正文。

以 **Agent 自进化**领域为例，具体拆分如下：

| 内容 | 放正文还是附录？ | 理由 |
| --- | --- | --- |
| 自进化机制的整体框架图 | **正文** | 核心贡献，不看就不懂你在做什么 |
| 自进化的触发条件与更新规则 | **正文** | 方法的灵魂，必须在正文讲清楚 |
| 主结果表（你的方法 vs Baselines） | **正文** | 核心 Claim 的数据支撑 |
| 消融实验（去掉自进化模块的效果） | **正文** | 直接证明你的核心设计是否有效 |
| Agent 的完整 Persona Prompt 模板 | **附录** | **复现需要**，但审稿人不需要逐字读完才能理解贡献 |
| 每一轮对话的详细 Log 示例 | **附录** | Case Study 正文放 1 个最精彩的，其余扔附录 |
| 所有超参数列表（temperature, buffer size...） | **附录** | 复现必备，但正文只需要展示关键超参即可 |
| 不同 LLM backbone 的对比（GPT-4o vs Claude vs Qwen） | **视情况** | 如果是核心 Claim 之一则正文，如果只是鲁棒性验证则附录 |
| 评测指标的数学定义 | **视情况** | 标准指标（Accuracy, F1）直接引用；自定义指标（EEO）必须在正文定义 |
| 计算资源与运行时间统计 | **附录** | 除非你的 Claim 包含"效率提升" |

### 附录的利用

问自己一个问题：**“如果不看这段话，读者还能理解我的核心贡献吗？”** 如果能，就移到附录。

- **必须移走的内容**：
    - 所有的 Prompt（提示词）全文。
    - 超级详细的 Hyperparameters（超参数）列表。
    - 冗长的数学推导证明（正文只放定理和最终公式）。
    - 具体的 Case Study 展示（正文留一个最精彩的即可）。
    - Baseline 的详细复现配置。

### 结果与讨论融合

不要把表格里的数字像报菜名一样念一遍。

- **❌ 常见写法**：
    
    > "In Table 1, Method A achieves 90% accuracy. Method B achieves 85%. Our method achieves 92%. This shows our method is best." (废话文学，浪费3行)
    > 
- **✅ 推荐写法**：
    
    > "As shown in Table 1, our method outperforms baselines by a margin of 2-7%, achieving 92% accuracy while maintaining low latency." (一句话概括优势和核心指标)
    > 

## LaTeX 结构优化

LaTeX 的默认格式里，标题（Heading）非常占地。

### 用 `\paragraph{}` 代替 `\subsection{}`

这是“省行神器”。

- **场景**：在 `Experiments` 或 `Related Work` 章节，如果你有很多小的分点（例如不同的 Ablation Studies）。
- **效果对比**：
    - `\subsection`：标题独占一行，且上下有巨大的空白间距。
    - `\paragraph`：**标题加粗后直接接正文，零垂直损耗。**

**例子：**

> Ablation on Component A. We remove A and observe a drop in... (Paragraph 模式)
vs.3.1 Ablation on Component A (Subsection 模式，这一行后面全是空白)
We remove A and observe a drop in...
> 

## 数学公式：能“躺”着就不“站”着

公式排版遵循“重要性原则”。

### 行内 (Inline) vs. 独行 (Display)

- **原则**：只有**核心贡献公式**（如你的 Loss Function、全新的建模公式）或者**特别长**的公式，才配用 `\begin{equation}` 独占一行。
- **操作**：简单的变量定义、集合描述、标准的贝叶斯公式等，可以塞进段落里。
- **例子**：
    - 【❌ 浪费】：
        
        > Let S be the set of samples:
         $S = \{x_1, x_2, ..., x_n\}$
        > 
    - 【✅ 精简】：
        
        > Let $S = \{x_1, \ldots, x_n\}$ be the set of samples...
        > 

## 语言精炼：句子要“脱水”

英文写作要直接、有力。把废话挤出去。

### 主语合并与从句化

将多个短句合并为紧凑的长句（但要注意保持清晰）。

- **❌ 啰嗦**：
    
    > "AgentMark uses a specific mechanism. This mechanism is called Contextual Key. It helps the model to identify users."
    > 
- **✅ 精简**：
    
    > "AgentMark employs a Contextual Key mechanism to facilitate user identification." (主语统一，动作直接)
    > 

### 拒绝 “元话语 Meta-talk”

不要告诉读者“我要开始分析了”或者“值得注意的是”，直接把结论端上来。

- **❌ 常见废话**：
    - "It is worth noting that..." (直接删)
    - "We can observe from the experimental results in Table 1 that..." (直接删)
    - "The results of the ablation study are presented in Figure 3." (无意义的指路)
- **✅ 推荐写法**：
    - "Table 1 shows that..."
    - "Notably, ..."
    - "Our method significantly reduces error rates (Fig. 3)." (把引用作为括号里的证据)

## 逻辑剪枝

### 避免重复定义

- 如果在 `Problem Formulation` 里已经定义了 x 是输入，y 是标签，在 `Method` 章节就不要再写“where x is input...”了。

### 引用代替解释

- **原则**：对于领域内公认的算法（如 Transformer 结构），**不要在你的论文里重新讲一遍课**。
- **操作**：直接写 "Following [Citation], we adopt the standard attention mechanism..."，把宝贵的篇幅留给**你自己独创的**部分。

## 列表与算法的“扁平化”

### 列表：从“垂直”变“水平”

`itemize` 和 `enumerate` 是吃行数大户。

- **❌ 垂直列表**：
    
    > We have three contributions:
    > 
    > - First, we propose A...
    > - Second, we design B...
    > - Third, we implement C...
    > *(这占了 4 行)*
- **✅ 行内列表 (Inline)**：
    
    > We have three contributions: (1) we propose A...; (2) we design B...; and (3) we implement C...
    (这只占 2 行)
    > 

### 算法伪代码

算法框图 (`algorithm` environment) 经常占掉半栏甚至一栏。

- **操作**：
    - **移除非核心步骤**：数据加载、初始化参数 `t=0` 这种废话直接删掉，只保留核心 Loop。
    - **改为数学公式**：如果算法逻辑不复杂，直接在正文里用公式描述步骤，不要用伪代码框。
    - **放附录**：如果算法流程很长但逻辑标准，正文只给 High-level 描述，伪代码扔附录。

## 消灭“孤儿词”

这是排版最后阶段的“挤牙膏”技术。

### 检查段落末尾

- **现象**：一个长段落的最后一行，只有 **1-2 个单词**。这 1-2 个单词就占了一整行的垂直空间。
- **操作**：**重写这一段**。删掉几个形容词，或者换个更短的同义词，把这 1-2 个词“吸”回上一行去。
    - *例子*：把 "utilize" 改成 "use"，把 "in order to" 改成 "to"。

### 检查页面末尾

- **现象**：一页的最后一行刚好是一个新 Section 的标题，或者只有正文的一行字。
- **操作**：使用 `\vspace{-0.5em}` 稍微调整段落间距（慎用，不要太明显），或者调整图表位置，把版面撑满或收紧。
    
    > 注意, 查看对应的投稿论文是否禁止使用 `\vspace`
    > 

## 论文精简参考步骤

| 现状分级 | 核心策略 | 操作注意事项 |
| --- | --- | --- |
| **严重超页 (> 2页)** | **结构重组与内容迁移**
优先执行附录迁移、多表合一及逻辑剪枝，实现物理空间的瞬间释放。 | **避免陷入低效的句式微调**
在结构未定型前进行文字润色是时间资源的浪费。 |
| **中度超页 (0.5 - 1页)** | **提升信息密度**
通过精简元话语、图注空间置换及标题结构降级，剔除冗余以提升信噪比。 | **严禁违规调整格式**
切勿通过缩小字号、行距或页边距来压缩空间，以免遭格式审查拒稿。 |
| **轻微超页 (5 - 10行)** | **排版微调与美学优化**
聚焦于孤儿词控制、公式内联化及图片白边裁切，进行像素级的空间收敛。 | **避免改动宏观逻辑**
此时不应再变动篇章结构，防止因改动引发上下文连贯性缺失  |

## 超页 2 页以上

当论文超页严重（>2页）时，应避免低效的句式微调，而应优先通过将非核心内容（如证明、超参、详细复现设置）迁移至附录以及合并冗余图表等结构性调整，以实现大幅度的篇幅压缩。

### 附录利用

这是最快的方法，瞬间释放 1-2 页空间。问自己：**“不看这个，审稿人能不能懂我的核心贡献？”**

- **必须移走**：
    - 所有的 **Prompts (提示词)** 全文。
    - 详细的 **Hyperparameters (超参数)** 列表。
    - **数学推导 (Proofs)**：正文只留 Theorem 和最终公式，推导过程扔附录。
    - **Baseline 细节**：复现的配置细节全部移走。
    - **额外的可视化**：只要保留最精彩的 Case，其他的扔附录。

### 多表合一

- **原则**：只要指标逻辑相似，就不要拆分。
- **操作**：如果 Table 1 算 Accuracy，Table 2 算 Efficiency，且模型列表一样，**强制合并**。利用 `\multicolumn` 共用表头。

### 逻辑剪枝

- **避免重复定义**：Problem Formulation 定义过的符号，Method 里不要再解释一遍。
- **引用代替解释**：对于通用的模块（如 Standard Attention, ResNet Block），直接写 `See [Citation]`，不要重新讲课。

## 超页 0.5 - 1 页

**当论文超页幅度适中（0.5-1页）时，主要问题通常在于语言冗余而非结构缺陷。此时应侧重于提升信息密度，通过精简元话语（Meta-talk）、将描述性细节下沉至图注（Captions）、以及降级标题结构等手段，剔除无效信息以释放空间。**

### 利用图注空间

- **原则**：正文只讲结论，图注负责解释设置。
- **操作**：把正文里关于“蓝色代表什么”、“误差棒代表什么”、“具体缩写定义”的句子，全部剪切到 `\caption{}` 里。

### 标题结构降级

- **操作**：在 `Experiments` 或 `Related Work` 章节，把所有的 `\subsection{Title}` 替换为 `\paragraph{Title.}`。
- **效果**：`\subsection` 独占一行且有大片空白；`\paragraph` 标题直接接正文，**零垂直损耗**。
    
    > 注意保持章节结构性质, 不要本末倒置了
    > 

### 列表扁平化

- **操作**：将占地巨大的 `itemize` 或 `enumerate` 列表，改为段落内的 `(1)...; (2)...`。
    
    > **⚠️ 特例**：**Introduction 中的 Contributions (创新点)** 是论文的核心卖点，为了保证视觉上的强调效果，**请保留垂直列表形式。**
    > 

### 消灭元话语

- **操作**：全篇搜索并删除以下废话：
    - ❌ "It is worth noting that..." → ✅ "Notably,..."
    - ❌ "We can observe from Table 1 that..." → ✅ "Table 1 shows..."
    - ❌ "In this section, we will introduce..." → (直接开始介绍)

## 超页 5 - 10 行

**当论文仅超页微量（5-10行）时，应避免改动整体逻辑以防破坏上下文连贯性。此时应聚焦于排版微调，通过优化段落末尾的“孤儿词”（Widow Control）、内联非核心公式、以及精简参考文献元数据等排版策略，在不损失内容的前提下完成最终的篇幅收敛。**

### 消灭“孤儿词” (Widow Control)

这是性价比最高的一招。

- **现象**：一个段落的最后一行，只有 **1-2 个单词**。这几个词就占了一整行的宝贵空间。
- **操作**：重写该段落的最后一句（删掉一个形容词，或换个短词），把这几个词“吸”回上一行。
    - *收益*：改一处就能省一行。

### 数学公式内联化

- **操作**：检查所有的 `\begin{equation}`。除了**核心贡献公式**和**超长公式**，其余简单的定义式（如 $S=\{x_1...\}$）全部改为行内 `$ ... $`。

### 图片白边裁切

- **操作**：使用 PDF 工具或脚本，把插图周围多余的白色边缘切掉，让图文排版更紧凑。

# **实验工程防坑指南：并发调度、自动化流与成本控制**

- 科研不仅拼脑力，也拼**算力调度**和**数据流工程**。
- 很多同学做实验时像“老牛拉车”：跑完一个 Seed，记录一下，再跑下一个；改完模型，对着 Log 文件一个个把数字放进 Excel 算平均分。
- **Pain Driven Development” (痛苦驱动开发)**
    - 第一次做这件事：手动做，没问题。
    - 第二次做这件事：觉得有点烦，还是手动做了。
    - **第三次做这件事**：必须写脚本！
    
    **请记住：任何需要机械重复超过 2 次的步骤，都应该脚本化。**
    

## 实验并行化

为了排除偶然性，我们通常需要跑 3 个随机种子。

- **❌ 串行傻跑**：
    
    > Run Seed 1 (4h) **->** Run Seed 2 (4h) **->** Run Seed 3 (4h) **= 12 小时**
    评语：如果显存够用，这是对生命的巨大浪费。
    > 
- **✅ 并行调度 (Parallel)**：
    
    > Run Seed 1 & Seed 2 & Seed 3 = 4 小时。
    > 

### **实操指南 (仅供参考)**

写一个简单的 Bash 脚本，利用后台运行符 `&`。

**关键点**：

1. **显存隔离**：确保显存不溢出（OOM）。如果一张卡跑不下，用 `CUDA_VISIBLE_DEVICES` 分配到不同卡上或者再开一台服务器
2. **输出隔离**：**这是最容易翻车的地方**。绝对不能让多个进程写同一个日志文件。
    
    > 可以根据不同的seed来区分结果文件
    > 

```bash
#!/bin/bash

# 定义要跑的 Seeds
seeds=(42 123 2024)

for seed in "${seeds[@]}"; do
    # 动态生成输出目录，防止文件冲突覆盖！
    OUTPUT_DIR="./results/experiment_v1/seed_${seed}"
    mkdir -p "$OUTPUT_DIR"

    echo "Starting experiment with seed $seed..."

    # 核心命令：
    # 1. > "$OUTPUT_DIR/log.txt" 2>&1 : 重定向所有输出到独立文件
    # 2. & : 放入后台并行执行
    CUDA_VISIBLE_DEVICES=0 python train.py \\
        --seed "$seed" \\
        --output_dir "$OUTPUT_DIR" \\
        > "$OUTPUT_DIR/train.log" 2>&1 &

    # 如果显存不够同时跑3个，可以在这里加个 sleep 或者逻辑控制
    # sleep 5
done

# 等待所有后台任务结束
wait
echo "All experiments finished!"

```

## 拒绝“手动填表”：分析脚本化

当你需要整理 Table 1 的结果时，如果你发现自己打开了 5 个 log 文件，打开 Excel，然后一个个复制粘贴数字，计算平均值…… **请马上停下来。**

因为你一定会改模型，一旦改了，这套流程就要重来一遍。手动操作不仅慢，而且容易填错行。

- **❌ 手工流**：打开 Log -> 复制 Accuracy -> 粘贴 Excel -> 拉公式算 Mean/Std -> 复制到 LaTeX。
- **✅ 脚本流**：运行 `python analyze_logs.py` -> 自动生成包含 Mean±Std 的 CSV 代码。

### **实操模板 (仅供参考)**

```python
import glob
import json
import pandas as pd
import numpy as np

# 1. 自动抓取所有 Seed 的结果文件
log_files = glob.glob("./results/experiment_v1/seed_*/metrics.json")
data = []

for f in log_files:
    with open(f, 'r') as file:
        log = json.load(file)
        # 提取你需要的一行数据
        data.append({
            'seed': log['seed'],
            'accuracy': log['test_accuracy'],
            'f1_score': log['test_f1']
        })

# 2. 转为 DataFrame 计算统计量
df = pd.read_json(json.dumps(data))

# 3. 自动计算 Mean 和 Std
summary = df.agg(['mean', 'std'])

# 4. 直接输出“论文格式”的字符串
acc_mean = summary['accuracy']['mean']
acc_std = summary['accuracy']['std']

print(f"Final Result for Table: {acc_mean:.2f} ± {acc_std:.2f}")
#甚至可以直接生成 LaTeX 格式, 不够也可以让AI来生成
# print(f"& {acc_mean:.2f} $_{{\\pm {acc_std:.2f}}}$ \\\\\\\\")
```

## 小规模数据集验证与模型成本控制

在启动耗时极长、成本高昂的大规模实验之前，务必进行小规模的“金丝雀验证”。

### **数据集覆盖：小而全**

- **原则**：你可以先测小规模数据集（如随机抽取 1% 的数据），但这个子集**必须包含整个数据集所有的边缘情况（Corner Cases）和数据要点**。
- **目标**：小规模测试不仅仅是为了跑通代码，更重要的是暴露数据分布不均、异常输入（如过长文本、特殊字符）导致的系统崩溃。如果小规模数据集缺乏代表性，一旦全量跑就会不断在长尾错误上挂掉，浪费大量时间。

### **模型选择：避免天价账单**

复现多智能体（Agent）论文或运行复杂对话系统时，模型 API 调用的成本极高。

- **先上“平替”模型**：在调试系统 prompt、Agent 交互逻辑和结果解析流水线时，**优先使用低成本模型（如国内大模型，或 Claude-3-Haiku、Gemini-Flash 等）进行测试**。
- **警惕开源代码的“Token 刺客”**：很多开源的 Agent 代码，在开发时**根本没有做 Token 节约优化**（例如循环传递冗余的历史记录、未经截断的检索上下文等）。如果你直接挂上 GPT-4o 或 Opus 跑大规模测试，可能会在一夜之间烧掉几百美元。
- **策略**：只有当系统在低成本模型上表现出预期的行为或跑通全链路后，再切换为高智商昂贵模型跑最终的正式实验结果。

# **代码匿名与开源**

- 在投稿双盲会议（Double-blind）时，如果需要在正文中提供代码链接，必须使用匿名代码托管平台（如 [**Anonymous GitHub**](https://anonymous.4open.science/)）。

在使用匿名平台生成链接前，请务必执行以下 **“脱敏清洗”** 步骤：

## 文件路径与密钥脱敏

检查代码中是否硬编码了个人路径或密钥。

- **❌ 危险写法**：
    
    ```python
    # 暴露了用户名 'Liam' 和具体的 API Key
    DATA_PATH = "C:/Users/Liam/Desktop/project/data"
    OPENAI_KEY = "sk-1234567890..."
    
    ```
    
- **✅ 安全写法**：
    
    ```python
    # 使用相对路径或环境变量
    DATA_PATH = "./data"
    OPENAI_KEY = os.getenv("OPENAI_API_KEY") # 或者留空 "YOUR_API_KEY"
    
    ```
    

## 语言与注释清洗

代码也是论文的一部分，保持专业性。

- **操作**：将所有的**中文注释**翻译成英文。中文注释不仅显得不专业，还可能暗示作者的国籍/地区，破坏匿名性。
- **❌ 例子**：`# 这里如果不加个延时，请求会报错`
- **✅ 例子**：`# Add a delay here to avoid request rate limit errors.`

## 隐蔽的身份信息

很多同学只记得删代码里的名字，却忘了配置文件。

- **LICENSE 文件**：标准的 MIT/Apache License 模板里通常包含 `Copyright (c) 202X [Author Name]`。**请务必删除年份后的名字，或改为 "Anonymous Authors"**。
- **配置文件**：检查 `setup.py`, `package.json`, `.git/config` 等文件中的 Author/Email 字段。
- **Git 提交记录**：匿名平台通常会自动隐藏 `.git` 文件夹，但如果你的代码里包含生成的 log 文件头部（header），可能会残留提交者信息。

## **代码匿名**推荐工具

- [**Anonymous GitHub**](https://anonymous.4open.science/)：
    - **优势**：可以直接克隆你的 GitHub 仓库并生成一个不可溯源的匿名链接，不需要你手动上传文件。
    - **注意**：它只是隐藏了仓库归属，**不会自动修改你代码里的内容**。上述的清洗工作必须由你手动完成。

> 注意设置是否 Auto update(自动同步更新) 和 Expiration date of the anonymized repository (确保审稿人在审稿的时候, 仓库没有过期)
> 
- 大多数审稿人确实不会真的去跑你的代码，但提供一个**规范、有效且长期存活**的匿名链接，是建立“可复现性”信任的关键。

### **关键配置解读**

1. **自动同步**
    - **投稿准备期（建议勾选）：**这样你在 GitHub 私有仓库里修了 Bug 或补了文档，匿名链接会自动同步更新。不需要你每次改完代码都重新生成链接。
        
        > 注意：同步有一定延迟（通常 1 小时内）。如果发现匿名页面内容未更新，请尝试**清除浏览器缓存**
        > 
    - **正式审稿期（建议关闭）**：**Deadline 截止后，建议取消勾选**。这样你可以在 GitHub 上继续大刀阔斧地开发（如重构代码、添加新 Feature），而不必担心破坏审稿人看到的“稳定快照”版本。
2. **过期策略** 
    - **⚠️ 绝对红线**：请选择 **"Never expire"** 或设置一个**足够长的时间**（至少覆盖 Rebuttal 和 Camera Ready 阶段，建议 1 年以上）。
    - *惨痛教训*：有同学设置了 "1 Month"，结果审稿人一个月后开始审稿，点开链接显示 "Repository Expired"，直接因为无法验证代码而给低分。
3. **后续修改**
    - 别担心，这些设置（包括要隐藏的文件规则）在生成链接后**都是可以随时修改的**。你只需要保存好生成后的链接即可。

## **两个战场，两套逻辑：投稿 vs. 开源**

这是很多人没有意识到的关键分野。

**你投稿时，面对的是审稿人（Reviewer）。**

审稿人的核心任务是**判断贡献是否有价值**，而不是真的去复现实验。

绝大多数审稿人不会 clone 你的仓库跑代码——他们要被你的**故事说服**。

所以论文的写作重心是：

- **Motivation 足够有力**：让审稿人觉得“这个问题值得解决”
- **Method 足够可信**：让审稿人相信“你的方案逻辑上是对的”
- **Result 足够清晰**：让审稿人觉得“数字在支持你的 claim”

**你开源时，面对的才是真正的同行（Peer Researcher）。**

这些人才是真正会 cite 你、复现你、在你工作上继续构建的人。他们会 clone 仓库、跑代码、读 README、改参数——他们会发现所有你没写清楚的地方。

所以 GitHub 开源的重心是：

- **可复现性（Reproducibility）**：环境、数据、超参都要写清楚
- **可扩展性（Extensibility）**：代码结构清晰，让人能在你基础上继续做
- **可理解性（Understandability）**：不只是能跑，还要能读懂

> **一句话总结**：论文是写给“判断者”看的，GitHub 是写给“使用者”看的。前者需要你说服，后者需要你服务。
> 

### **写作手法与开源侧重的核心差异**

| **维度** | **论文投稿** | **GitHub 开源** |
| --- | --- | --- |
| **核心目标** | 说服审稿人接收 | 让同行能复现和引用 |
| **受众行为** | 阅读、判断，通常不运行代码 | Clone、运行、修改、扩展 |
| **重点内容** | Motivation + Insight + 核心结果 | 环境配置 + 数据准备 + 代码结构 |
| **Prompt/超参** | 放附录，正文不必全写 | **必须完整公开**，否则无法复现 |
| **代码质量要求** | 能支撑核心实验即可 | 需要模块化、可读，方便二次开发 |
| **结果呈现** | 数字漂亮，显著优于 Baseline | 数字必须能被别人跑出来，可复现 |
| **细节省略策略** | 为节省篇幅，大量细节下沉至附录 | 必须在 README 或注释中**补全**这些细节 |

### **GitHub 开源的额外侧重点**

当论文正式接收后代码开源，受众从“审稿人”切换为“真实引用者”，需要额外关注：

1. **补全论文里省略的细节**
    
    论文为了节省篇幅，大量实现细节被移到附录甚至完全省略。但代码仓库是给**要跑通你实验的人**看的，必须把这些“论文里砍掉的血肉”长回来。复现者卡死的地方，几乎都是论文里一笔带过的代码细节：
    
    - **超参数与配置文件**：论文里可能只写了“learning rate = 1e-4”，但实际跑通还需要 warmup steps、scheduler 类型、batch size、gradient accumulation 等一整套配置。开源时应提供完整的 config 文件（如 configs/main_experiment.yaml），而不是让复现者去猜。
    - **数据预处理管线**：论文经常用“We preprocess the data following [Citation]”一句话带过，但复现者最常卡死在这里。开源时必须提供从原始数据到模型输入的**完整处理脚本**，包括分词、清洗、划分、格式转换等每一步。
    - **Prompt 全文**：论文正文通常只展示 Prompt 的核心片段或设计思路，完整 Prompt 被扔进附录甚至省略。开源时必须在代码中给出**可直接运行的完整 Prompt 模板**，包括 System Prompt、Few-shot 示例等。
    - **非显然的 Bug Fix 与 Trick**：如果你在实验中踩过坑（如某个 API 版本不兼容、某个 loss 需要 clip），请在代码注释里说明原因，而不是留一行“神秘代码”让复现者抓狂。
    
    > **判断标准**：想象一个刚读完你论文、对你的方法感兴趣的博士生，clone 了仓库。他能不能**不问你任何问题**就跑通主实验？如果不能，缺的就是你要补的。
    > 
2. **提供 Reproducibility Checklist**
    
    明确告诉别人：哪个脚本对应论文里的哪张表/图。
    
    - *例子*：`# This script reproduces Table 2 (Main Results) in the paper`
3. **主动维护 Issue 区**
    
    真正会 cite 你的人，往往会在 Issue 里提问。及时回复不仅能帮助同行，还能发现代码潜在问题，甚至催生新的合作机会。
    

## README 规范与结构

- **代码库不仅要“能跑”，还要“好读”。**
    
    一个结构清晰、文档齐全的 README 是对审稿人的最大尊重，在一定程度上能提升论文被接收的概率
    
- **“把审稿人当成第一天复现论文的小白。”**
    
    不要假设审稿人知道该配什么环境变量，也不要假设他们知道数据该解压到哪里。步骤写得越无脑（Copy-Paste 就能跑），你的代码可信度就越高。

# 正文与附录的拆分提交策略

- 在绝大多数顶级会议（如 ICML, NeurIPS, CVPR, ICLR）的投稿系统中，**正文 (Main Paper)** 和 **补充材料 (Supplementary Material)** 是需要作为两个独立的 PDF 文件上传的。
- 为了避免在 Deadline 前手忙脚乱地修改引用，请严格遵循以下“先合后分”的撰写流程。
- 如果你觉得有效拆分中的方案 B 太复杂，搞不定 `xr` 宏包，那就老老实实**用方案 A**。
    
    **“笨办法但能跑”永远优于“高级办法但报错”。**
    
    但在最后拆分前，一定要保留一份“整合版”的最终定稿作为备份，以防万一。
    

## 写作阶段：整体撰写

在撰写初稿和修改阶段，可以不用将正文和附录拆成两个 LaTeX 项目。

- **操作**：将所有内容写在同一个 `.tex` 项目里。附录部分使用 `\appendix` 命令开始，接在 `\bibliography` 之后。
- **优势**：
    - **交叉引用自动化**：正文中引用附录定理时，直接用 `\ref{thm:proof1}`，LaTeX 会自动处理编号。
    - **批改便利**：不需要在两个 PDF 之间切来切去，逻辑连贯。

## 提交阶段：有效拆分

- 到了正式提交前夕，我们需要将一份代码编译成两个 PDF，同时**保持引用链接不失效**。
- 这里有两种流派，**推荐使用方案 B**。

### 方案 A：硬编码法—— *简单粗暴，适合新手*

这是最直观的方法，适合 LaTeX 技能一般的同学。

1. **备份项目**：复制整个文件夹，分别命名为 `Main_Project` 和 `Supp_Project`。
2. **处理正文 (`Main_Project`)**：
    - 删掉 `\appendix` 后面的所有内容。
    - **关键步骤**：找到所有引用附录的地方（如 `See Appendix \ref{sec:proof}`），手动改为硬编码文本：`See Appendix A`。
    - *缺点*：如果附录章节顺序变了，你得手动改回来，容易出错。
3. **处理附录 (`Supp_Project`)**：
    - 删掉正文内容，直接以 `\appendix` 开头。
    - *注意*：为了保持计数器连续（比如正文用了 Table 1，附录应该是 Table 2），需要手动重置计数器：`\setcounter{table}{1}`。

### 方案 B：`xr` 宏包法 —— *专业优雅，强烈推荐*

这是学术界的标准做法，可以实现在两个独立的 PDF 之间互相引用，且点击链接可跳转。

1. **准备工作**：将你的 `main.tex` 拆分为 `paper.tex` (正文) 和 `supplementary.tex` (附录)。
2. **在 `paper.tex` 中**：
    - 正常写，不要包含附录内容。
3. **在 `supplementary.tex` 中**：
    - 引入 `xr` 宏包：
        
        ```latex
        \usepackage{xr}
        \externaldocument{paper} % 读取 paper.aux 中的引用信息
        
        ```
        
    - 这样你在附录里引用 `\ref{fig:main_result}` 时，LaTeX 知道它是正文里的图 3。
4. **编译顺序**：
    - 先编译 `paper.tex` -> 生成 `paper.aux`。
    - 再编译 `supplementary.tex` -> 它读取 `paper.aux` -> 引用正常显示。

### **在 Overleaf 中使用 xr 宏包**

[参考教程](https://blog.csdn.net/xovee/article/details/107564551)

Overleaf 无法直接读取隐藏的 `.aux` 文件，需通过配置文件实现。

1. **新建配置**：在项目根目录新建文件，命名为 `latexmkrc`（无后缀）。
2. **写入代码**：将以下代码粘贴进去（假设正文文件名为 `paper.tex`）：
    
    ```perl
    # 编译完 paper.tex 后，将其 aux 文件另存为 paper_copy.aux
    system("pdflatex paper.tex");
    system("cp paper.aux paper_copy.aux");
    
    ```
    
3. **引用设置**：在 `supplementary.tex` 中引入宏包并指向副本：
    
    ```latex
    \usepackage{xr}
    \externaldocument{paper_copy} % 注意这里引用的是 copy 版
    
    ```
    
    > 在 \externaldocument{...} 里，填的名字是你**复制出来**的那个文件名（即 paper_copy），而**不是**原本的正文文件名（paper）
    > 
    > 
    > **原因**：Overleaf 的编译机制会频繁清空/重写原始的 paper.aux。为了防止读取错误，我们在 latexmkrc 里把生成好的 aux 文件**另存为**了一个叫 paper_copy.aux 的副本。所以你的附录文件必须去读这个副本，才能稳定获取引用信息
    > 
4. **编译**：直接编译 `supplementary.tex` 即可（latexmkrc 会自动先编译 paper 生成 aux）。

## 提交前的最终检查

无论用哪种方法，提交前必须检查以下三点：

- **匿名性**：附录的标题页有没有不小心写上作者名字？
- **引用有效性**：正文里的 "See Appendix A" 是否真的对应附录里的 Section A？
- **文件大小**：有些会议对 Supplementary Material 也有大小限制（如 100MB），如果图太多，记得压缩。

# Rebuttal 到 Camera Ready：如何优雅地兑现承诺

很多同学以为论文被接收（Accept）就万事大吉了。但从 Rebuttal 到 Camera Ready，中间还有一次关键的“兑现”过程。这一步做不好，轻则浪费你 Rebuttal 里的努力，重则破坏一篇本已被认可的好论文。

## 先搞清楚：Rebuttal 和 Camera Ready 的受众完全不同

这是很多人没有意识到的关键区别，而它决定了你在两个阶段的行为逻辑。

### Rebuttal：说服领域专家

Rebuttal 的受众是**审稿人（Reviewer）**

他们是你这个子领域的专家，带着具体的技术质疑来审你的论文。你需要：

- **逐条回应**他们的 Concern
- **补充实验**证明你的 Claim
- **用数据和逻辑说服**他们改变评分

这是一场高强度的**学术辩论**，对手是懂行的人。

### Camera Ready：通过编辑的格式审查

Camera Ready 的受众切换为**编辑（Editor / Publication Chair）**。他们关心的是：

- 排版是否符合模板规范？
- 页数是否在限制内？
- 作者信息是否补全？
- 参考文献格式是否正确？

**编辑通常不会重新审查你的技术内容。** 这就是为什么有些人在 Rebuttal 里承诺“We will add this experiment in the camera-ready version”，最后什么都没加，论文照样出版

因为 Camera Ready 阶段没有人再做技术审查了。

## 为什么我们仍然要兑现 Rebuttal 的承诺？

上面说的“什么都不改也能过”是事实，但请不要这样做。原因有三：

1. **学术诚信是底线**
    
    你在 Rebuttal 里写的每一句“We will...”，都是对审稿人和学术社区的承诺。审稿人基于你的承诺提了分，你不兑现，本质上是一种学术失信。正是这类行为的积累，导致越来越多审稿人对 Rebuttal 里的“承诺”持怀疑态度，“他说会加实验，但我不信他真的会加”，长此以往，伤害的是整个学术审稿体系的信任基础。
    
2. **缺少核心实验的论文，长期来看会被同行质疑**
    
    论文发表不是终点，而是起点。你的同行（真正会 cite 你、复现你的人）迟早会发现论文里缺少的东西。一篇“故事讲得好但实验不扎实”的论文，引用量和影响力都会大打折扣。
    
3. **作为学风优良的实验室，我们追求知行合一**
    
    我们做科研不是为了“发了就行”，而是为了对社区真正有益。Rebuttal 里补充的实验往往是审稿人帮你发现的盲区。这些补充会让你的工作更加完整和可信。
    

## 核心原则：轻改正文，重补附录

现在问题来了：要兑现承诺，但**怎么改**？

很多同学的第一反应是大刀阔斧地重写正文：重组 Section 结构、重写 Method 描述、把 Rebuttal 里的新实验塞进正文的 Experiment 章节……

**这是最危险的做法。**

### 为什么不能大改正文？

你要相信一个事实：**当时你提交的论文，是一个经过多轮打磨的作品。审稿人认可的也是那个整体。**

论文被接收，说明审稿人对你的**叙事结构、逻辑链条、实验布局**已经形成了认知模型。你在 Camera Ready 阶段大幅改动正文：

- **可能破坏原有的叙事节奏**：你以为在“优化”，实际上可能打乱了审稿人当初认可的逻辑流。
- **可能引入新的不一致**：改了 Method 的描述，Experiment 的表述没跟着改，前后就矛盾了。
- **高投入，负收益**：付出了大量时间精力，结果论文反而不如原版连贯。

> **类比**：一幅已经被画廊接受的油画，你可以修补一些细微的瑕疵，但如果你把整个构图推翻重画，画廊不一定会更满意，他们买的就是原来那幅。
> 

## 正文只做“微创手术”

Camera Ready 正文的修改，应该严格控制在以下范围：

| 可以改 | 不要改 |
| --- | --- |
| Typo（错别字、语法错误） | Section 的整体结构和顺序 |
| 符号错用 | Method 的核心描述逻辑 |
| 图表中的标注小错误 | 删除或替换已有的实验表格 |
| 补全作者信息、致谢 | 重写 Introduction 的叙事框架 |

## 补充实验通过附录 + Ref Hook

Rebuttal 里承诺的补充实验、额外分析、新的 Ablation Study，**全部放进附录**。

大多数顶会的 Camera Ready 对附录页数**没有限制**（或限制很宽松），这是你的“无限弹药库”。

**操作方法**：

1. **在附录中新建 Section**，完整呈现补充实验：
    
    ```latex
      \appendix
      \section{Additional Experiments from Reviewer Feedback}
      \label{sec:additional_exp}
    
      Following the valuable suggestions from reviewers, we conduct
      additional experiments to further validate our claims...
    ```
    
2. **在正文中用一句话 + ref 引用过去**（这就是“Ref Hook”）：
    
    ```latex
      % 在正文 Experiment 章节的合适位置，加一句话
      We further validate this finding with additional experiments
      on [new dataset/setting], with detailed results provided in
      Appendix~\ref{sec:additional_exp}.
    ```
    
3. **正文改动量**：仅增加 1-2 句话，不破坏任何现有段落结构。

### Ref Hook 的几种常见写法

根据补充内容的类型，正文中的 Hook 句式略有不同：

- **补充实验**：
“We provide additional results on [X] in Appendix \ref{sec:xxx}, which further support our claim in Section 3.2.”
- **回应审稿人的具体质疑**：
“To address the concern regarding [Y], we conduct a dedicated analysis in Appendix \ref{sec:yyy}, confirming that [结论].”
- **扩展到新场景**：
“We further extend our evaluation to [Z] (see Appendix \ref{sec:zzz}), demonstrating the generalizability of our approach.”

> **技巧**：Hook 句子的措辞要让读者感觉这是论文“自然延伸”的一部分，而不是“被审稿人逼着补的”。用 “further validate”、“extend”、“complement” 这类积极动词，而不是 “address the concern” 这种防御性措辞（后者只适合出现在 Rebuttal Letter 里，不适合出现在论文正文中）。
> 

## Camera Ready 的完整检查清单

在提交 Camera Ready 之前，按顺序过一遍：

| 检查项 | 说明 |
| --- | --- |
| **Rebuttal 承诺追溯** | 逐条检查 Rebuttal 里的每一个 “We will...”，确认都已兑现（附录中有对应内容，正文中有 Ref Hook） |
| **正文 Diff 检查** | 用 latexdiff 工具对比初稿和 Camera Ready 版本，确认正文改动幅度可控 |
| **匿名信息恢复** | 补回作者姓名、单位、致谢（Acknowledgement）、资助信息（Funding） |
| **格式合规** | 确认使用了会议提供的 Camera Ready 模板（通常和投稿模板不同！注意页眉、版权声明等） |
| **附录完整性** | 确认附录中的补充实验都有完整的表格/图表，不要只有文字描述 |
| **超链接检查** | 确认正文中所有指向附录的 \ref{} 都能正确跳转，没有出现 “??” |

> **推荐工具**：latexdiff old.tex new.tex > diff.tex 可以生成一份标注了所有改动的 PDF（新增内容标蓝，删除内容标红）。这不仅方便自查，如果会议要求提交“changes summary”，这份 Diff 文档也可以直接用。
