# 架构合并垃圾回收指引 (Architecture GC)

## 概述

在项目经历重大架构合并或升级后，代码仓库中往往残留大量死链、孤儿文档、未引用资产和空目录。
手动清理耗时且容易遗漏，本 Skill 通过 **自动扫描 → 语义冲突检测 → 分级处置方案 → 人类审批执行** 的四步流程，
系统化地完成工程环境的熵减工作。

与常规做法的区别：
- 不是简单的 `find + rm`，而是基于文档引用图谱进行语义级分析
- 所有破坏性操作必须经人类审批，Agent 绝不自作主张
- 内置零残留自检，确保清理后无新增问题

## 使用方式

### 第一步：非破坏性扫描

运行扫描脚本收集残留对象：

python scripts/gc_[scanner.py](http://scanner.py) [目标目录，默认 .]

脚本输出四类数据：
| 类别 | 说明 |
|------|------|
| Dead Links | 文档中引用但本地已不存在的路径 |
| Orphan MD | 未被任何文档或索引引用的游离 Markdown |
| Orphan Assets | 未被任何 Markdown 引用的图片资源 |
| Empty Dirs | 不含任何文件的空目录 |

### 第二步：语义冲突检测

以 `ARCHITECTURE.md` 最新版本为基准，用 `grep` 收集历史文档中仍在使用的已废弃模块名称。
**输出变更确认申请单，列明新旧概念与引用链路，交由人类决策。**

### 第三步：生成分级处置方案

按危险性分为四级：
- 🔴 **立即删除** — 违背新架构的废弃文件 / 零依赖废弃资产（须人类批准）
- 🟠 **归档降级** — 移至 `history/` 并标记废弃，保留历史价值（须人类批准）
- 🟡 **内容刷新** — 修复遗留文件中的断链和过时引用
- 🟢 **安全保留** — 无需变更

### 第四步：执行与验证

等待人类对 🔴🟠 级别变更作出 Approved / 否决 后：
1. 执行文档移除或更新
2. 清理未引用资产
3. **必须再次运行** `python scripts/gc_scanner.py` 进行零残留自检

## Gotchas（踩坑点）

- ⚠️ **Symlink 不追踪**：扫描器默认跳过符号链接，monorepo 中跨 workspace 的 symlink 引用可能被误判为死链
- ⚠️ **隐藏文件/目录被跳过**：以 `.` 开头的文件和目录（如 `.github/`）不在扫描范围内，需要手动检查
- ⚠️ **仅识别 Markdown 链接语法**：`]()` 格式以外的引用方式（如 HTML `<img>` 标签、代码中的路径常量）不会被检测
- ⚠️ **index 文件免疫**：`README.md`、`AGENTS.md`、`ARCHITECTURE.md` 等被视为根节点，即使未被引用也不会标记为孤儿
- ⚠️ **`.gitignore` 中的文件**：被 git 忽略但物理存在的文件仍会被扫描，可能产生误报
- ⚠️ **`node_modules` / `third_party` 硬编码跳过**：如果项目使用其他命名的第三方目录，需要手动调整脚本

## 参考文件

- `scripts/gc_scanner.py` — 核心扫描脚本，输出死链 / 孤儿文件 / 孤儿资产 / 空目录四类报告
- `ARCHITECTURE.md` — 项目架构基准文档，语义冲突检测的对照源
- `history/` — 归档降级文件的存放目录（按需创建）
